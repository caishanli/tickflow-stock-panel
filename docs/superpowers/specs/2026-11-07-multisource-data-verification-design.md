## 1. 背景

本地 `data/` 下的行情分区是回测、模拟盘、前端的唯一事实来源。现状是「写进去就信」：
落盘前没有独立核验，出问题只能等事后发现。

已经发生过的事故：

| 日期 | 事故 | 后果 |
|---|---|---|
| 2026-10-22 | 回补写入前复权价，写进不复权契约的 `kline_daily` | 股票 165 个分区 + 部分 ETF 被重复复权，前复权价偏 18%~58% |
| 2026-09-10 | mootdx 全市场 K 线失效，当天分钟只落了尾段 | 9-10 上午整段缺失，且腾讯只够回补 3.3 个交易日，差点永久丢 |
| 2026-11-07 | **本次实测新发现**（见 §2） | 科创板分钟成交量/成交额 ×100，已持续约 60 个交易日 |

现有检查的覆盖范围：

- `data_integrity.py`：只查**分区存在性**和 `quote_ts` 盘中快照，不看数值；
- `daily_basis_repair.py`：baostock 对拍，但只覆盖日线/ETF 日线基差，且是手动 CLI；
- `adj_factor_quality.py`：只做因子序列跳变隔离。

**缺的是：多源数值一致性校验 + 自动修复 + 可复查的报告。**

## 2. 本次实测发现（设计依据）

### 2.1 科创板分钟量额 ×100（真实污染）

`kline_minute` 聚合到日线后与 `kline_daily` 对比，688/689 的比值恒为 **100**：

```
2026-08-03  688 symbols=612  ratio≈100: 0     ratio≈1: 612
2026-09-09  688 symbols=616  ratio≈100: 0     ratio≈1: 614
2026-09-10  688 symbols=613  ratio≈100: 613   ratio≈1: 0
2026-10-23  688 symbols=617  ratio≈100: 617   ratio≈1: 0
2026-11-06  688 symbols=616  ratio≈100: 616   ratio≈1: 0
```

分界点正好是腾讯分钟回源接管（09-10 当天已由腾讯回补，所以从 09-10 起就是 ×100）。
**修复必须按「检测到的比值」判定，不能按日期切**——09-10 之前的个别残片日也可能被腾讯补过。
根因在
`backend/app/services/tencent_minute.py::parse_m1_rows`：无条件 `vol = r[5] * 100`。
腾讯 `mkline` 对主板返回「手」，对科创板（688/689）返回的已经是「股」。
证据：688001 当日 15:00 收盘竞价原始量 95429，而全天日线量 86305.59 手
（= 8,630,559 股），原始值当「股」解释才自洽。

影响：约 60 个交易日 × 616 只的 `kline_minute.volume/amount` 全部放大 100 倍。
分钟级量价指标（VWAP、量比、分钟成交额）在这些标的上全错。

### 2.2 提前收盘日会误报（判定规则要能区分）

2016-01-04（熔断首日，13:33 提前收盘）600004：

- 本地分钟：最后一根有量 bar 13:35 收 13.27，之后到 15:00 全为 0 量平推 13.27；
- 本地日线 / baostock：收 13.04、低 12.81、量 120912 手；
- 腾讯日线：收 13.27、量 120912 手。

即「分钟→日线」聚合直接用 `last(close)` 会在提前收盘/停牌日误报。**核验必须分层：
硬错误（结构、单位、缺段）直接判错；收盘价类差异要按特殊交易日规则归类，且需外部源佐证才修。**

## 3. 目标 / 非目标

### 目标

1. 覆盖 5 个数据集、**最大历史口径**：
   `kline_daily`（2016-01-04 起，2633 分区）、`kline_etf_daily`（2005-02-23 起，5275 分区）、
   `kline_index_daily`（2025-07-31 起，307 分区）、`kline_minute`（2016-01-04 起，28GB）、
   `kline_etf_minute`（2026-04-01 起，441MB），外加复权因子表。
2. 多源交叉确认：每个结论至少两个独立来源，或明确标记 `single_source`。
3. 能确定性修复的自动修，修不动的隔离并报告。
4. 全流程可重入、断点续跑、可干跑（dry-run）。
5. 修复前后可复查：备份 + receipt + 状态 JSON + JobStore 进度。

### 必须一并修的生产端

只修历史不改生产端 = 核验器每天和回源链路对打。因此 **M1 同时修
`tencent_minute.parse_m1_rows` 的量单位规则**（科创板 688/689 原样入库、其余 ×100），
并补回归测试。判定用「代码前缀 → 单位」映射，不按日期。

### 修完必须重算下游

`kline_daily` / `kline_etf_daily` 修好后，`kline_daily_enriched` / `kline_etf_enriched`
不会自动失效（增量只算不存在的日期）。因此修复流程的最后一步是**只针对本次实际修过的
日期**执行 `prune_enriched_partitions` + 对应日期的 pipeline 重算，失败不回滚已修数据，
只记入报告。`kline_minute` / `kline_etf_minute` 没有下游派生表，不需要这一步。

### 非目标

- 不改读侧契约（`kline_daily`/`kline_etf_daily` 仍存不复权原始价，读侧乘因子）。
- 不核验「今天」的数据（盘中还在变）。
- 不引入新的主行情源；`eltdx` 只作为独立第三方核验/回补手段，可选依赖。
- 不改前端读路径；隔离清单暂时只进报告，不改变回测取数行为（后续单独立项）。

## 4. 核验分层

### L0 结构（无网络，全历史）

每个分区逐 symbol 检查：

- 分区存在；symbol 集合与当日应有宇宙比对（允许停牌/未上市，需登记原因）；
- bar 数：股票 241、ETF 241（特殊日按实际交易分钟数放行，见 §5.3）；
- 时间戳：`09:30` 起、`11:30` 止、`13:01` 起、`15:00` 止，无 `13:00` bar，无重复、严格递增；
- 数值：`volume>=0`、`amount>=0`、`low<=min(open,close)<=max(open,close)<=high`、无 NaN/Inf；
- 行情非空但全 0 量（停牌日除外）→ 可疑。

### L1 内部一致性（无网络，全历史）

`1min → 日线` 聚合（`open=first, high=max, low=min, close=last, volume=sum, amount=sum`）
与同日 `kline_daily` / `kline_etf_daily` 对拍。这一层是**覆盖全部历史的关键**：
外部 1min 源最多只有 94 个交易日，但日线有 10 年，且日线本身可由外部源核验。

必须先做**单位归一**（§5.1），否则会把单位问题误判成数值问题。

### L2 外部一致性

| 数据集 | 主核验源 | 覆盖 | 次核验源 |
|---|---|---|---|
| 股票日线 | 通达信官网盘后包（HTTP，2.7MB/日，沪深北全市场，含成交额） | 2021-08-16 起 | baostock 日线（2016 起，抽样/分批）、腾讯（抽样） |
| 2021 前股票日线 | baostock 日线 | 2016–2021 | 腾讯日线（`fqkline`，不复权） |
| ETF 日线 | 腾讯 / baostock | 2005 起（baostock ETF 仅 2026-01 起） | 本地 → L1 |
| 指数日线 | 腾讯 / 新浪 | 2025-07 起 | TickFlow raw |
| 股票 1min | eltdx（`all_pages`，22560 根 ≈ 94 交易日） | 近 94 交易日 | 腾讯 800 根（3.3 日）、新浪 1023 根（4.2 日）、baostock 5min 聚合 |
| 更早的 1min | **无独立 1min 源** | — | 只能 L0+L1 |
| ETF 1min | 腾讯 / 新浪 / eltdx | 2026-04 起 | L1 |
| 复权因子 | xdxr 事件重算 + 腾讯 qfq 反推 | 全历史 | baostock 事件 |

## 5. 判定规则

### 5.1 单位契约（硬性）

| 表 | 字段 | 单位 |
|---|---|---|
| `kline_daily`（股票） | volume | 手 |
| `kline_etf_daily` | volume | 股 |
| `kline_minute` | volume | 股 |
| `kline_etf_minute` | volume | 股 |
| 腾讯 `mkline` 主板/ETF 原始量 | 手 | 入库 ×100 |
| 腾讯 `mkline` **科创板 688/689** 原始量 | **股** | **不得 ×100** |
| 腾讯 `mkline` 科创板 amount | 无字段，按 `vol × typical` 估算 | 与量同尺度 |
| 新浪 1min `volume` | 股 | 直接入库 |
| baostock 日线 `volume` | 股 | ÷100 后比对 |
| `kline_index_daily` | volume | 股（腾讯日线给手，×100 后比对） |
| 腾讯日线（指数） | 无 amount | 指数 amount 只比本地内部一致，不跨源 |

单位表进代码常量，并由 L1 每天自检（ratio 分布异常即告警）。

**成交额的特殊处理**：腾讯 `mkline` 没有 amount 字段，落盘时按 `vol × (H+L+C)/3` 估算，
实测与日线成交额偏差 p5–p95 约 0.5%~1%、极端可到更高。因此：

- 分钟 amount 的跨源容差放宽到 2%，且判定为 `soft`；
- **分钟 amount 永不作为修复依据**（不作为仲裁票）；
- 分钟成交额只在 L1 做量级校验（比如 100× 这种量级错误仍能抓到）。

### 5.2 容差

- 价格：绝对 1 tick（0.01，ETF/低价股按 0.001）+ 相对 0.1%；
- 成交量/成交额：相对 0.5%（跨源口径差异）；
- 一致性判定：`max(绝对容差, 相对容差)`。

### 5.3 特殊交易日（避免误报）

不维护「特殊日白名单」，用可判定的信号：

- **提前收盘**：当日最后一根 `volume>0` 的 bar 早于 15:00（或分钟覆盖 < 241 根且尾部全 0 量）；
  此时分钟收盘价取最后一根有量 bar，日线收盘若仍有差异则记 `soft`；
- **停牌**：分钟全 0 量、日线量 0，属正常；
- **新股上市首日、退市整理期**：bar 数可能不足 241，按实际放行；
- **集合竞价**：`09:30` bar 含 09:25 竞价量，不单独校验；
- **`09:30` 前/`15:00` 后出现 bar**：直接判 L0 错误。

交易日历以 `app/services/trade_calendar.py`（随包种子 + 运行期刷新）为准；
「某只票当天该不该有数据」用**缺口启发式**：该 symbol 在前一交易日和后一交易日都有数据、
当天既无日线也无分钟 → 记为缺失；仅单侧有 → 记 `soft`（可能是停牌/退市）。
这样不需要维护停牌表，也不会在停牌日刷屏。

### 5.4 仲裁

优先级（高→低）：`交易所官方 / TickFlow raw` > `通达信盘后包` > `baostock` > `腾讯` > `新浪` > `本地存量`。

- 至少两个**外部**来源一致 → 按该结论修复，标记 `confirmed`；
- 只有单来源 → 修复但标记 `single_source`，并在报告里单列；
- 来源互相矛盾（无多数）→ 不修，进隔离清单，标记 `conflict`。

**关于 provenance**：分区没有来源列，也不打算新增（会破坏读侧 schema）。本设计里的
「两个独立来源」指**外部源之间互相独立且一致**，本地数据只是被检查对象，不参与投票。
因此不需要记录每行的来源，也不需要按日期猜来源。

## 6. 修复策略

### 6.1 可确定性修复

- **科创板分钟 ×100**：直接 `volume/100`、`amount/100`，并用 L1 复核 ratio≈1。
  这类不依赖外部网络，可全历史批量执行。
- 重复行 / 时间戳越界 / OHLC 非法：按行剔除或按相邻 bar 重建，需 L1 复核。

### 6.2 可由外部源覆盖

- 日线：用盘后包整分区重写（原子替换，先备份）；
- 分钟（近 94 交易日）：用 eltdx 按 symbol 重拉，按 `(symbol, datetime)` 覆盖；
- 复权因子：用 xdxr 事件重建后整表替换，旧表备份。

### 6.3 无法修复

- 更早的分钟数据（无独立源）：写入隔离清单 `data/data_verify_quarantine.json`，
  报告里列出 `table/day/symbol/reason`，**不删除任何数据**；
- 是否让回测/模拟盘跳过隔离数据，作为后续独立需求。

### 6.4 安全阀与自动修复口径

- 修复前备份到 `data/data_verify_backup/<run_id>/<table>/date=...`；
- 只修已收盘交易日（`day < today`）；
- 手动全量跑：默认 dry-run，`--apply` 才写；
- **每日定时跑（自动）：只自动应用两类**
  1. 确定性类（单位换算、重复行、时间戳越界、OHLC 非法）；
  2. 近 7 个交易日内、`confirmed` 的外部覆盖；
  其余一律只报告。任何单分区改动超过 5% 行的自动修复降级为报告，需 `--force`；
- 与实时写盘互斥：修复只碰已收盘分区，写入用原子替换（temp + `os.replace`）；
- 修复期间不占用 `try_acquire_run_slot`（不阻塞回测/repair_daily），但要在状态里标明
  正在核验，并在结束时让 `invalidate_storage_cache()` 失效缓存。

### 6.5 下游重算（修复后置阶段）

- 仅当日线族（`kline_daily` / `kline_etf_daily` / `kline_index_daily`）发生实际写入时才触发；
- 范围 = 本次修复涉及的日期集合，按族分别 `prune_enriched_partitions` 后重跑 pipeline；
- 重算失败只记 `report.recompute_failed`，不影响已完成的修复；
- 分钟族不触发重算（没有 enriched 派生表）。

## 7. 执行形态

### 7.1 代码结构

```
backend/app/quant/data_verify/
  __init__.py
  units.py             # 单位契约 + 归一
  findings.py          # Finding 模型与错误码
  checks_structure.py  # L0
  checks_internal.py   # L1 分钟→日线
  checks_external.py   # L2 外部比对
  checks_factors.py    # qfq 口径
  probes/              # tdx_package / tencent_m1 / sina_m1 / eltdx_m1
  policy.py            # 仲裁 + 修复决策
  repair.py            # 备份、原子写、缩放/替换、receipt
  recompute.py         # enriched 失效与重算
  runner.py            # 分批/断点/进度
  report.py            # 状态 JSON + 隔离清单
```

CLI：`python -m app.quant.data_verify --stage structural|internal|external|factors|all [--apply] [--resume]`

### 7.2 调度与进程边界

- **全部核验/修复逻辑跑在主后端进程**（能拿到 JobStore、repo、`quote_service`、API 状态），
  不放进 stockdata 服务子进程——那边没有 JobStore，`_SYNC_LOCK` 也只在子进程内有效。
- 与 15:35 写盘链路的互斥靠**数据边界**而不是跨进程锁：核验只处理 `day < today` 的
  已收盘分区，写入用原子替换；15:35 链路只写当日/缺失分区，两者不重叠。
- **每日增量**：收盘后核验最近 7 个交易日（定时任务注册在主后端），自动修 §6.4 规定的两类；
- **全量历史**：一次性 JobStore 任务，分批跑，可中断续跑；
- 启动自检沿用 `data_integrity.boot_integrity_check` 的入口，扩展为「结构 + 增量核验」。

### 7.3 性能预算

- 分钟分区聚合实测 ~0.1s/分区（Polars，1.2M 行）；2633 个分区单遍约 5 分钟，IO 28GB 是主要成本；
- 盘后包 1 次 HTTP/日，2021-08 起约 1300 个包 ≈ 3.5GB 流量，可分批；
- baostock 慢（单次查询秒级），只用于抽样/缺口，不做全市场逐日；
- 全量核验期间限制并发（2 worker），并且只在非交易时段跑。

## 8. 报告

- `data/data_verify_status.json`：最近一次运行时间、阶段、发现数、修复数、隔离数、各源可用性；
- `data/data_verify_receipts/<run_id>.json`：逐条修复记录（表/日/代码/字段/旧值/新值/依据源）；
- 日志：`WARNING` 级别摘要 + `INFO` 明细；
- API：`GET /api/settings/data-verify/status`（复用现有 settings 通知机制）；
- 前端：先在 settings 页以文本卡片展示，不新建页面。

### 验收口径

1. 能复现并修复 §2.1 的科创板 ×100（修复后 L1 ratio≈1）；
2. 对 2026-10-22 历史事故区间（2023-04-19..2023-12-20）能报出异常并给出与 `daily_basis_repair` 一致的结论；
3. 2016-01-04 / 2018-06-01 的收盘价差异被归为 `soft`，不触发自动覆盖；
4. 全量结构扫描 0 崩溃，断点续跑不重复写；
5. 修复全过程有备份，且 `--dry-run` 与 `--apply` 的判定结果一致。

## 9. 里程碑

1. **M1 单位与结构**：单位表 + L0 + 科创板修复（立即价值，不依赖外部源）；
2. **M2 日线全历史**：盘后包适配 + baostock 抽样 + 自动修复；
3. **M3 分钟全历史**：L1 全量 + eltdx 近 94 日 + 腾讯/新浪抽检；
4. **M4 复权核验**：xdxr 重建对照 + 腾讯 qfq 反推；
5. **M5 日常化**：每日增量、状态 JSON、settings 展示。

## 10. 风险与待定

- `eltdx` 是第三方同协议客户端（`a-stock-data` skill 明确不引入同类库）。**已确认：只作为
  核验/回补的可选依赖**（`--extra verify`），不进入主取数链路；加载失败时 M3 自动退化为
  腾讯/新浪 3~4 日 + baostock 5min 抽样。
- baostock 实测不可靠：2026-11-07 单日 5min 查询挂起 >180s，区间查询 >240s 无返回（日线查询正常）。
  因此 baostock 5min 只做抽样核验，必须带硬超时（≤60s）、重试与跳过。
- 2016 年以前的分钟数据没有任何独立 1min 源，只能靠 L0+L1；这是口径边界，报告里必须写明。
- 盘后包只到 2021-08-16；更早只能 baostock/腾讯逐只，成本高，默认抽样。
- 全量扫描会与实盘争 IO；默认只在非交易时段跑，并限 2 并发。
- 修复覆盖用户手工改过的数据：备份 + dry-run 默认 + receipt 可回溯。
